## Обновление 2026-11-01 — постоянное имя DuckDNS

Основной адрес: [каталог](https://quttyqonaq.duckdns.org/apartments), [кабинет](https://quttyqonaq.duckdns.org/login). DuckDNS указывает на сервер Oracle, Caddy выдаёт и обновляет сертификат HTTPS, а `APP_URL` приложения настроен на новый адрес. При создании и копировании ссылок на договоры с Oracle используется этот адрес. Render продолжает использовать собственный адрес для ранее выданных ссылок.

Старый адрес `rentalsign.161-33-183-103.sslip.io` перенаправляет запросы на DuckDNS с сохранением пути и параметров. Это перенаправление работает, пока прежний IP принадлежит серверу и доступен; если IP будет утрачен, ссылки со старым адресом могут перестать работать. Ссылки, уже отправленные на Render, по-прежнему зависят от Render.

Таймер `rentalsign-duckdns.timer` запускает обновление приблизительно раз в пять минут; DuckDNS определяет публичный IPv4 по исходящему подключению сервера. При изменении IP DNS обновляется после следующего успешного запуска; также нужно дождаться окончания кеширования DNS. Если виртуальная машина удалена или полностью недоступна, обновление на ней не запустится: при восстановлении на новом сервере настройку и ключ необходимо перенести или изменить запись вручную. Бесплатный адрес зависит от доступности и условий DuckDNS и не является гарантией бесперебойной работы.

Ключ API хранится в `/etc/rentalsign/duckdns-token`, владелец root, права 600. Он относится ко всему аккаунту DuckDNS и позволяет изменять также другие домены аккаунта, включая Qosyl; не размещайте его в репозитории или журналах. При смене ключа потребуется обновить все использующие его настройки. Исходники сервиса и таймера для восстановления сохранены в [deploy/oracle](../deploy/oracle/); серверный скрипт установлен в `/usr/local/sbin/rentalsign-duckdns-update`. Проверка состояния:

```sh
sudo systemctl start rentalsign-duckdns.service
systemctl show rentalsign-duckdns.service --property=Result,ExecMainStatus
systemctl list-timers rentalsign-duckdns.timer --no-pager
sudo journalctl -u rentalsign-duckdns.service -n 20 --no-pager
```

Для восстановления после безопасного размещения ключа с правами 600 выполните из корня проекта:

```sh
sudo install -o root -g root -m 700 deploy/oracle/duckdns-update.py /usr/local/sbin/rentalsign-duckdns-update
sudo install -o root -g root -m 644 deploy/oracle/rentalsign-duckdns.service deploy/oracle/rentalsign-duckdns.timer /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl start rentalsign-duckdns.service
sudo systemctl enable --now rentalsign-duckdns.timer
```

Проверены валидный HTTPS, DNS обоих доменов, журнал успешного обновления, включённый таймер, вход и существующие объекты/договоры, действующая ссылка и PDF на новом адресе и через старый адрес, а также новый адрес в ответе кабинета для действующей ссылки. Отдельно проверены успех, неверный ключ и ошибка сети для скрипта с подставными ответами. Реальное изменение IP и восстановление удалённой машины не имитировались.

## Облачная конфигурация

`render.yaml`: один Node.js web-сервис, plan=free, без disks/databases, регион Frankfurt. Автодеплой отключён: публикации запускаются после проверки исходников. Команды:

```text
npm ci --include=dev && npm run build:cloud && npm prune --omit=dev
npm run start:production
```

Серверный адрес берётся из `RENDER_EXTERNAL_URL`, установленного Render. Для собственного домена можно явно задать HTTPS-origin в APP_URL. Не оставляйте APP_URL=http://localhost:3000 на сервере: это неверные ссылки и отказ CSRF-проверки.

Секреты задаются в настройках провайдера, а не в исходниках:

| Переменная           | Значение                                                                      |
| -------------------- | ----------------------------------------------------------------------------- |
| DATABASE_PROVIDER    | postgresql                                                                    |
| DATABASE_URL         | Neon PostgreSQL connection URL, TLS sslmode=require; рекомендуется pooled URL |
| DIRECT_DATABASE_URL  | Прямой Neon URL для миграций, TLS sslmode=require                             |
| TOKEN_ENCRYPTION_KEY | 32 случайных байта в hex; сохранять при любых рестартах                       |
| ADMIN_EMAIL          | Email первоначального администратора; также владелец каталога, если `CATALOG_OWNER_EMAIL` не задан |
| CATALOG_OWNER_EMAIL | Необязательный email единственного владельца публичных галерей, иначе используется `ADMIN_EMAIL` |
| ADMIN_PASSWORD       | Случайный пароль 12–128 символов; только для первого запуска                  |

`start:production` проверяет origin, ключ, диапазоны сроков и TLS, применяет PostgreSQL-миграции и создаёт администратора только при пустой таблице Admin. Повторный старт не сбрасывает пароль, не создаёт публичных тестовых аккаунтов и не запускает seed. `/api/health` возвращает 200 только при доступной мигрированной базе, иначе 503; ответ не раскрывает параметры подключения.

Для SQLite на отдельном сервере также поддерживается production-init с абсолютным DATABASE_URL, но этот вариант требует постоянного диска и **не используется** в бесплатной облачной конфигурации.

Не пересылайте локальный `.env` или SQLite через публичный репозиторий.

## Проверка после размещения

1. Подтвердить live-развёртывание и точную ревизию источников.
2. Проверить HTTPS `/api/health`, `/login`, отказ анонимному административному API.
3. Проверить авторизованное чтение без создания или изменения записей, если владелец предоставил доступ для такой проверки.
4. Сквозное создание вымышленных объектов и договоров, выпуск ссылок, демодействие, PDF и конкурентные операции выполнять на отдельной тестовой базе, не на базе реальных клиентов.
5. Доступность ранее выданных ссылок проверять только безопасным согласованным способом, не раскрывая и не записывая токены. Порядок совместного обновления Oracle и Render — в [OPERATIONS.md](OPERATIONS.md).

Демопредупреждение остаётся обязательным; внешнее размещение не делает действие ЭЦП. Сценарии проверяются исключительно на вымышленных данных.

`scripts/check-cloud.ts` отдельно проверяет реальный PostgreSQL: два sign одновременно, гонки sign/отзыв и sign/замена ссылки. Он создаёт явно вымышленные записи и требует `DATABASE_PROVIDER=postgresql` и `CLOUD_SMOKE_ALLOW_WRITES=1`. Перед запуском сгенерируйте PostgreSQL-клиент; для возврата к локальной SQLite-разработке выполните `npm run db:generate`. Не запускайте эту проверку на базе реальных клиентов.

MCP создания сервиса не поддерживает настройку healthCheckPath; в реально созданном сервисе остаётся стандартная проверка Render, а `/api/health` проверяется отдельно по HTTP. В Blueprint для будущего создания указан `/api/health`.

## Ограничения бесплатных тарифов

Render Free засыпает после 15 минут простоя, первый запрос запускает сервис заново и может ждать около минуты. Квота Free compute разделяется с другими бесплатными сервисами аккаунта. Платные улучшения не включены. Расписание обращений описано ниже.

Neon Free имеет ограниченные storage/compute/transfer квоты. При достижении лимита работу нужно ограничить или пересмотреть размещение с владельцем; автоматически переключаться на платный план запрещено. Бесплатный поддомен не является приобретённым доменом второго уровня. Доступность сторонних бесплатных сервисов не гарантируется.

Источники: [Render Free](https://render.com/docs/free), [переменные Render](https://render.com/docs/environment-variables), [Neon Free](https://neon.com/docs/introduction/plans).

Файл оставлен только для ручной проверки здоровья; для её запуска потребуется вручную включить workflow. Автоматических обращений из этого workflow больше нет. Render Free может засыпать после 15 минут без входящего трафика; первый посетитель после простоя может ждать запуска около минуты.
