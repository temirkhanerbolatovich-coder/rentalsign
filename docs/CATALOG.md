# Каталог квартир и оформление договора

Каталог расширяет существующий сценарий RentalSign: посетитель выбирает квартиру, владелец согласовывает условия и создаёт договор, арендатор читает его по персональной ссылке и получает демонстрационный PDF. Отдельного исходного файла ТЗ при добавлении каталога в репозитории не найдено; основание интеграции — текущие README, ARCHITECTURE, API и реализованный сценарий договоров.

## Что предоставлено

Источники — исходная папка `квартиры` и дополнительный ZIP с 21 фотографией, предоставленный 2026-10-18. После уточнения привязки фотографии опубликованы для 7 объектов: всего 90 снимков. Адреса Базовая 2/6 и Михаэлиса 8/2 подтверждены владельцем вместо слитного написания в названиях папок. Диапазоны цен сохраняются без подмены фиксированной суммой.

У Михаэлиса, 8, кв. 69 отсутствует цена; карточка показывает «Цена по запросу». Предоставленная позднее ссылка 2ГИС добавлена. Неизвестные площадь, число комнат, вместимость, удобства и занятость не выводятся как факты. Период цены хранится отдельно (`day`, `month`, `unconfirmed`); до подтверждения карточки явно требуют уточнить период.

## Сценарий

1. Посетитель открывает `/apartments`, ищет адрес и сравнивает фотографии и цены. Цена в каталоге — ориентир для согласования; свободные даты не вычисляются.
2. `/apartments/:slug` показывает все предоставленные фотографии, этаж, подъезд и внешний переход в 2ГИС, если ссылка есть.
3. «Подготовить договор» ведёт на вход для владельца. Выбранный известный slug сохраняется после входа; произвольный redirect URL не принимается. Арендатору предлагается получить ссылку на договор от владельца.
4. Кнопка «Добавить объект и продолжить» выполняет авторизованный POST, создаёт отдельный объект владельца с `catalogSlug` и открывает форму с предвыбором. Чтение страниц ничего в БД не создаёт. Повторный POST возвращает тот же объект, не перезаписывает адрес/цену/описание владельца; архивный объект требует восстановления в «Объектах».
5. Владелец вводит общую стоимость за весь срок и депозит. Тариф каталога не считается итоговой суммой автоматически. Для объекта каталога нулевая итоговая стоимость отклоняется и интерфейсом, и сервером.
6. Далее работает существующий процесс: черновик → неизменяемая версия и персональная ссылка → ознакомление/демоподписание → PDF и журнал. Фотографии и 2ГИС не изменяют состав отправленного снимка договора.

## Хранение и обновление

`src/catalog/apartments.ts` — проверенный публичный перечень, `public/apartments/` — оптимизированные WebP. `scripts/import-catalog.ts` воспроизводит данные и изображения из исходной папки; исходные JPEG не изменяются. Источник цен/ссылок отделён от папки снимков, поскольку первоначальные названия галерей оказались перепутаны. Дополнительные JPEG из ZIP хранятся в отдельной подпапке Михаэлиса, 7. Фотографии поворачиваются по EXIF и сохраняются без исходных метаданных. Имя WebP включает хеш содержимого: заменённый снимок получает новый URL, поэтому кеш Next.js/браузера не показывает прежние фотографии. Только устаревшие обработанные WebP удаляются после успешного импорта; оригиналы сохраняются. Обложки и сведения задаются явно; изображение не служит источником выдуманных характеристик.

Каталог не читает приватные `Property` и не публикует демообъекты владельцев. `Property.catalogSlug` — необязательная связь; уникальность пары `ownerId/catalogSlug` предотвращает дубли в пределах аккаунта. SQLite и PostgreSQL имеют отдельные добавочные миграции `202610180001_catalog_link`. Перед запуском обновлённой версии выполните `npm run db:migrate`; production-init применяет облачную миграцию при старте. Ранее созданные объекты и договоры сохраняются.

Изменения перечня/фотографий требуют сборки и размещения новой версии. Редактирование приватного объекта не меняет публичную карточку, а изменение карточки не переписывает частные объекты и отправленные договоры. Это намеренное ограничение первого каталога; CMS/загрузка через кабинет потребуют отдельной задачи.

## Проверки и границы

Проверки перечислены в TESTING.md: полнота набора, ссылки/цены, поиск, сортировка, галерея, мобильная ширина, неизвестная карточка, изоляция владельцев, CSRF, повторный импорт, архив и общая сумма договора. Исходные фото остаются в пользовательской папке; в публикуемую часть входят только выбранные данные и обработанные изображения.

Автобронирование, календарь занятости, заявки, оплата, контактный WhatsApp владельца, реальная ЭЦП и юридическая проверка не реализованы этой интеграцией. Контакт для публичного каталога не выбран; реквизиты из предоставленного образца договора автоматически не становятся публичным контактом. Для полноценного бронирования нужны правила доступности, подтверждения и отмены, контакт владельца и отдельные требования.

По последующей просьбе владельца образец DOCX стал основой заранее подготовленного шаблона новых договоров. Обезличенные условия доступны для правки в `/templates`, реквизиты владельца хранятся только в закрытых настройках БД. Старые договоры не меняются; персональные сведения в публичный каталог не переносятся. См. [ADMIN_WORKSPACE.md](ADMIN_WORKSPACE.md).

Для квартир на Базовой, 4 и Есенберлина, 46 гостям показано напоминание брать с собой ключ от домофона. Содержимое сохранённых договоров не меняется.

По выбору владельца сети и пароли Wi-Fi показаны публично на страницах шести квартир и хранятся в публичном репозитории. Для Есенберлина данные Wi-Fi не предоставлены. При смене пароля необходимо обновить каталог и опубликовать новую версию; прежние значения останутся в истории Git.
